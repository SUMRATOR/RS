## 0. Обязательные правила

### 0.1. Целостность спецификации

При изменении спецификации ИИ-агент отправляет **весь обновлённый документ целиком**, а не отдельные изменения.

Запрещены сокращения многоточием, диффы и выдача части документа за полный документ. Разделение на сообщения допускается только с явного разрешения пользователя. Оптимизация и объединение повторяющихся требований допускаются по разрешению пользователя.

После утверждения версии ИИ-агент не изменяет спецификацию без прямого разрешения пользователя.

### 0.2. Разработка через Python-скрипты

Основной способ разработки — законченные автоматические Python-скрипты для Windows и IDLE:

1. Агент предоставляет готовый скрипт.
2. Пользователь сохраняет его в корне проекта.
3. Пользователь запускает его в IDLE клавишей F5.
4. Скрипт создаёт резервные копии, выполняет установку, проверки и выводит понятный отчёт.
5. При ошибке не допускается частичная установка либо выполняется восстановление.
6. Повторный запуск не должен дублировать изменения.

Предпочтительно: **один функциональный пакет — один установочный скрипт**.

**Имена всех новых скриптов разработки должны оканчиваться на `_F.py`.** Это относится к установочным, диагностическим, проверочным, миграционным и сборочным Python-скриптам.

Пример: `RS_CUSTOM_OBJECT_TYPES_INSTALL_V6_F.py`.

Требование не относится к модулям приложения, таким как `database.py` и `config.py`. Существующие скрипты документируются под фактическими именами; автоматическое переименование не требуется. При обращении к другому скрипту учитывается его фактическое имя, включая `_F.py`.

Обязательные требования:

- Определять корень проекта через `Path(__file__).resolve().parent`.
- Не использовать жёстко заданные пути к профилю пользователя или конкретному диску.
- Учитывать перенос проекта между компьютерами.
- Перед изменением файлов создавать резервные копии.
- Перед миграцией SQLite использовать SQLite Backup API.
- До и после миграции выполнять `integrity_check` и `foreign_key_check`.
- Учитывать, что SQLite исходников и EXE — разные физические файлы и могут иметь разные схемы.
- Не заменять одну пользовательскую SQLite копией другой без явно выбранного пользователем решения.
- Не создавать пустую SQLite как замену отсутствующей пользовательской базе при исправлении пути или миграции.
- Отличать исправление потерянной базы от штатного создания новой базы при первом запуске приложения.
- Согласовывать изменения ORM, сервисов, UI и схемы БД.
- Для сложных изменений предусматривать транзакции, восстановление и повторный безопасный запуск.
- Учитывать Windows CRLF при поиске и сравнении содержимого файлов.
- Собирать новую EXE отдельно и не заменять старую до функциональной проверки.
- Не считать успешную сборку PyInstaller доказательством работоспособности.
- Не использовать старую EXE с несовместимой схемой SQLite.
- Различать автоматические тесты, проверку настоящего UI пользователем и проверку EXE.
- При проверке диаграмм учитывать встроенный JavaScript и поведение браузера; проверка Python AST этого не заменяет.

Запрещено без необходимости вручную редактировать множество файлов, переписывать рабочий код целиком, удалять пользовательские данные, менять рабочую SQLite без резервной копии, подменять установку бесконечной диагностикой или объявлять непроверенную функцию готовой.

Диагностика допустима, если без неё изменение нельзя выполнить безопасно.

Пользователь разрешает разработку и экспериментирование, включая риск повреждения тестовых диаграмм. Это не разрешает незаметно уничтожать реальные пользовательские данные.

### 0.3. Подтверждение результатов

Различать:

1. **Установлено в исходниках** — код добавлен или изменён.
2. **Автоматически проверено** — прошли конкретные тесты или проверки.
3. **Проверено пользователем в UI** — пользователь подтвердил сценарий.
4. **Проверено в EXE** — пользователь подтвердил сценарий в автономной сборке.
5. **Принято** — выполнены согласованные критерии приёмки.

По рабочей договорённости фраза пользователя «дальше» означает, что предыдущий этап проверен и можно переходить к следующему. Она не заменяет подробного перечня проверенных сценариев и не означает автоматической приёмки всего модуля.

## 1. Назначение проекта

Rubik Studio — собственное Desktop/Web-приложение для моделирования, анализа и автоматизации бизнес-процессов, Process Mining, BPMS и архитектуры предприятия.

Функциональные ориентиры — SILA UNION, ARIS и другие системы; код и интерфейс должны быть собственными.

Основные возможности:

- Несколько независимых логических баз в одной физической БД.
- Репозиторий объектов и связей каждой логической базы.
- Методологии и каталог типов диаграмм.
- Графическое моделирование и повторное использование объектов.
- BPMN 2.0, Process Mining, BPMS и совместная работа.
- Автономная Windows-сборка и серверный режим.

Аудитория: студенты, преподаватели, аналитики, специалисты по бизнес-процессам и начинающие пользователи. Основной язык интерфейса — русский.

Принципы: единое Python-приложение, независимое от UI ядро, async-first, расширяемость, доступность, Open Source, защита от ошибок, аудит, собственный визуальный стиль и поэтапная реализация.

### 1.1. Режимы

| Запуск | `python -m rubik_studio` | `python -m rubik_studio --server` |

### 2.6. SQLite исходников и EXE

SQLite исходников и EXE — отдельные физические файлы.

В ранее обнаруженной старой SQLite EXE отсутствовали:

- `object_types.database_id`;
- `object_types.is_system`;
- `objects.database_id`;
- `object_links.database_id`;
- `model_element_bindings.database_id`;
- `audit_logs.database_id`.

При этом проверки `integrity_check` и `foreign_key_check` не обнаружили повреждений.

По явному подтверждению пользователя впоследствии была создана **отдельная копия базы исходников** для конкретного экземпляра EXE, а конфигурация этого экземпляра переключена на копию. Старая база EXE осталась на месте. Данные из старой базы EXE в копию не переносились.

Проверка копии подтвердила:

- `integrity_check` — `ok`;
- `foreign_key_check` — без нарушений;
- наличие проверенных таблиц и столбцов текущей ORM.

Это не доказывает полного совпадения всех индексов, ограничений и триггеров.

Автоматическая подмена пользовательских баз не допускается. Безопасная миграция старых пользовательских баз остаётся отдельной задачей.

Триггеры V3 `check_object_type_database` и `check_object_type_database_update` проверяют тип при вставке/изменении объекта, но изменение принадлежности самого типа может обойти эту защиту. Новая SQLite, созданная только ORM `create_all`, не получает эти триггеры автоматически. Полноценная защита на уровне БД ещё не подтверждена.

## 3. Логические базы, объекты и моделирование

### 3.1. Изоляция

Одна физическая SQLite/PostgreSQL содержит несколько независимых логических баз. Каждая база имеет UUID, собственную методологию, модели, объекты, связи и привязки.

Правила:

1. Модель и пользовательский объект принадлежат одной базе.
2. Все сервисы проверяют `database_id`; БД обеспечивает дополнительные ограничения.
3. Межбазовые связи и привязки запрещены.
4. Одинаковые названия в разных базах допустимы.
5. Изменения и удаление одной базы не затрагивают другие.
6. Названия баз выбирает пользователь; обязательные категории баз не вводятся.
7. UUID существующего объекта не меняется.
8. Прямой перенос объекта между базами запрещён. Отдельная операция копирования допускается с новым UUID, без автоматического копирования связей и привязок и без изменения исходного объекта.
9. Общие системные типы доступны всем базам, но не связывают между собой пользовательские объекты и базы.
10. Пользовательский тип принадлежит только одной базе.

### 3.2. Основной сценарий моделирования

Пользователь должен иметь возможность:

1. Создать логическую базу.
2. Создать в её репозитории объект нужного типа.
3. Заранее заполнить название, описание и необходимые доступные атрибуты.
4. Создать модель в той же базе.
5. Найти готовый объект в редакторе и добавить его на диаграмму как графический элемент.
6. Продолжить построение процесса и сохранить модель.

Под «импортом» готового объекта внутри базы понимается **добавление на диаграмму с привязкой к существующему объекту репозитория**, а не создание независимой копии.

Объект репозитория и его визуальное представление различаются:

- UUID, название, описание и общие атрибуты принадлежат объекту репозитория.
- Положение, размер и другие свойства конкретного размещения принадлежат диаграмме или её элементу.
- Один объект может использоваться на нескольких диаграммах своей базы.
- Изменения общих данных должны отображаться во всех его представлениях после обновления или повторного открытия модели; механизм актуализации и обработка одновременного редактирования требуют проверки.
- Удаление размещения с диаграммы не должно автоматически удалять объект из репозитория.
- Удаление используемого объекта требует проверки зависимостей и понятного предупреждения.
- Не каждый графический элемент, в том числе технический элемент BPMN, обязан становиться общим объектом.
- Добавление объекта из другой базы запрещено.

Экспериментальное размещение объектов и сохранение диаграмм реализованы; полная проверка перечисленных требований ещё не завершена.

### 3.3. Типы и трафареты: вопрос для согласования

Пользователь рассматривает типы как возможные средства связи баз или заготовки для однотипных процессов.

Предложенная, но ещё не утверждённая трактовка:

- тип объекта — заготовка для отдельных объектов, потенциально со схемой атрибутов и значениями по умолчанию;
- трафарет процесса — отдельный шаблон нескольких элементов и связей;
- общие системные типы не создают межбазовых связей;
- копирование между базами остаётся отдельной операцией с новым UUID.

До подтверждения пользователем не считать эту трактовку окончательным решением и не нарушать действующие правила изоляции. Существующий V6 управляет пользовательскими типами; полноценные трафареты процессов не реализованы.

### 3.4. Методологии и создание моделей

Встроенные методологии: `STANDARD` — стандартная, `EXTENDED` — расширенная, `FULL` — полная.

Методология определяет разрешённые типы моделей, категории, объекты, связи и инструменты. `FULL` означает полный каталог, а не готовность всех редакторов.

Для создания модели указываются название, база, тип и необязательное описание. Проверяются база, методология, тип, наличие работающего редактора и права. Неготовый редактор блокирует обычное создание модели.

Отдельно предусмотрены явно обозначенные экспериментальные типы согласно §3.5. Их наличие не делает готовыми обычные редакторы нотаций.

### 3.5. Экспериментальные диаграммы

Создание выполняется через **«Создать… → Диаграмму»**. Отдельную кнопку «Диаграммы базы» вводить не требуется.

Предусмотрены:

| Тип | Код | Состояние |
|---|---|---|
| Техническое полотно | `RS_EXPERIMENTAL_CANVAS_V22` | Экспериментальное, не нотация |
| BPMN 2.0 — экспериментальная | `RS_BPMN_EXPERIMENTAL_V40` | Экспериментальное, использует текущий верстак |

Оба служебных типа используют статус `NOT_IMPLEMENTED`. Нельзя менять реальные статусы нотаций на готовые только ради доступа к экспериментальному редактору.

При создании экспериментальной модели проверяются база, методология и хранилище V14. Категория, тип, разрешение методологии и модель создаются в одной транзакции.

Старый технический JSON-черновик V13 автоматически в новое хранилище не переносился. Его нельзя удалять или заменять без отдельного решения.

### 3.6. Связи репозитория и диаграммы

Существующие связи репозитория должны автоматически отображаться, когда на диаграмме присутствуют оба связанных объекта.

Экспериментальный механизм V23 получает связи репозитория и отображает их без копирования в `rs_diagram_edges`. При повторных размещениях предусмотрено отображение комбинаций размещений связанных объектов.

Удаление размещения не должно удалять объект или связь репозитория. После повторного открытия диаграммы отображение должно актуализироваться.

Технические линии диаграммы и связи репозитория различаются. Их удаление и редактирование должны быть понятны пользователю и не должны затрагивать несвязанные сущности.

### 3.7. Удаление используемого объекта

Проверка использования объекта должна учитывать:

- связи репозитория;
- привязки моделей;
- размещения объекта в `rs_diagram_nodes`;
- другие будущие ссылки на объект.

Ранее `RepositoryService.count_usages` учитывал `ObjectLink` и `ModelElementBinding`, но не учитывал `rs_diagram_nodes`. Следовательно, проверка удаления используемого объекта пока не считается полной.

## 6. Схема данных и хранение

Ниже целевые поля; фактические отличия указаны отдельно. UUID, связи и пользовательские данные сохраняются при миграциях.

### 6.1. Репозиторий

**`object_types`:** `id` UUID PK, `code` String(50), `name` String(200), `icon` String(50), `color` String(7), `database_id` UUID nullable, `is_system` Boolean. Системный тип общий, пользовательский принадлежит базе. `code` глобально уникален в физической БД.

**`objects`:** `id` UUID PK, `database_id` UUID NOT NULL, `type_id` UUID, `name` String(500), `description` Text, `attributes` JSON, `created_at`, `updated_at`. FK базы и типа, `UNIQUE(id, database_id)`, индекс `(database_id, type_id, name)`. Сервис запрещает дубликаты нормализованных названий в пределах базы и типа. Тип должен быть системным либо принадлежать той же базе.

**Атрибуты V4:** строки — JSON string, числа — JSON number, логические значения — JSON boolean, дата:

```json
{"__rs_type__": "date", "value": "2026-10-28"}
```

Дальнейшие требования: единый реестр определений, схемы для системных и пользовательских типов, обязательные и необязательные поля, типизация, значения по умолчанию, перечисления, ссылки на объекты той же базы, аудит и безопасная совместимая миграция. Атрибуты V4 нельзя терять.

**`object_links`:** `id`, `database_id`, `source_id`, `target_id`, `link_type` String(50), `attributes` JSON. `UNIQUE(database_id, source_id, target_id, link_type)`; составные FK `(source_id, database_id)` и `(target_id, database_id)`. Базовые отношения: `USES`, `RESPONSIBLE_FOR`, `GENERATES`, `MITIGATES`, `SUPPORTS`. Межбазовые связи запрещены.

Сервисные методы существуют. Полноценное управление всеми сценариями связей и интеграцию с редакторами требуется завершить и проверить.

### 6.2. Модели

**`models`, целевая схема:** `id`, `database_id`, `model_type_id`, `name` String(500), `description`, `content_format`, `content`, `version`, `created_at`, `updated_at`; `UNIQUE(id, database_id)`, индекс `(database_id, model_type_id)`.

Фактическая ORM содержала `id`, `database_id`, `model_type_id`, `name`, `description`, `created_at`, `updated_at`. `content_format`, `content`, `version` требуют согласованной миграции, если будут необходимы. Экспериментальное полотно использует отдельные таблицы §6.6.

**`bpmn_models`, целевая схема:** `id`, `database_id`, `model_type_id`, `name`, `description`, `xml_content`, `version`, `created_at`, `updated_at`. Фактическая ORM ранее не содержала `database_id` и `model_type_id`. До полноценного BPMN-редактора определить связь с `models` и учесть существующие FK из `process_definitions`.

**`model_element_bindings`:** `id`, `database_id`, `model_id`, `bpmn_element_id`, `object_id`; `UNIQUE(model_id, bpmn_element_id)`, составные FK и совпадение базы модели и объекта. Составные FK ранее установлены в мигрированной SQLite; полноценные интеграционные проверки с редакторами не выполнены. При развитии универсального полотна согласовать идентификаторы элементов разных редакторов без потери совместимости.

### 6.3. Mining, пользователи, аудит и BPMS

**`event_logs`:** целевые `id`, `database_id` nullable, `name`, `source`, `row_count`, `uploaded_at`. Ранее ORM не содержала `database_id`; учесть при реализации Mining.

**`events`:** `id` BigInt/SQLite INTEGER PRIMARY KEY, `log_id`, `case_id`, `activity`, `timestamp`, `resource`, `attributes`; индексы по `log_id`, `case_id`, `timestamp`.

**`users`:** `id`, `username`, `display_name`, `password_hash`, `role`, `is_active`, `created_at`; роли `admin`, `user`, `viewer`.

**`audit_logs`:** `id`, `timestamp`, `user_id`, `username`, `ip_address`, `action`, `entity_type`, `entity_id`, `entity_name`, `database_id`, `details`. Операции внутри базы передают `database_id`.

**`process_definitions`:** `id`, `model_id`, `code`, `name`, `version`, `is_active`, `created_at`.

**`process_instances`:** `id`, `definition_id`, `status`, `started_at`, `ended_at`, `started_by`, `variables`, `spiff_state`; статусы `RUNNING`, `COMPLETED`, `SUSPENDED`, `CANCELLED`, `ERROR`.

**`tasks`:** `id`, `process_instance_id`, `bpmn_task_id`, `name`, `description`, `status`, `assignee_id`, `assignee_name`, `candidate_group`, `form_data`, `due_date`, `created_at`, `completed_at`.

**`task_history`:** `id`, `task_id`, `timestamp`, `user_id`, `action`, `details`.

### 6.4. Базы, методологии и каталог

**`modeling_databases`:** целевые `id`, `name` String(500), `description`, `methodology_id`, `created_at`, `updated_at`, `created_by`, `is_archived`. Название уникально в экземпляре. Ранее ORM не содержала `created_by`, `is_archived`.

**`methodologies`:** целевые `id`, `code`, `name`, `description`, `is_system`, `is_active`, `created_at`; ранее ORM содержала первые четыре поля.

**`methodology_model_types`:** составной PK и UNIQUE `(methodology_id, model_type_id)`.

**`model_categories`:** `id`, `code`, `name`, `description`, `icon`, `sort_order`.

**`model_types`:** целевые `id`, `code`, `category_id`, `name`, `description`, `purpose`, `keywords`, `difficulty`, `implementation_status`, `editor_code`, `icon`, `is_active`, `sort_order`.

Фактическая ORM использует `editor_status`; согласовать при развитии без потери данных.

### 6.5. Seed и целостность

При первом запуске: 30 системных типов, администратор, три методологии, категории и встроенный каталог. Логические базы автоматически не создаются. Для сетевого Server стандартный пароль `admin/admin` недопустим без обязательной смены.

Seed ищет типы по коду, сохраняет UUID, не создаёт дубликатов и не удаляет пользовательские типы. V5 проверена на временной SQLite; полную интеграцию и все сценарии EXE необходимо дополнительно проверить.

SQLite: `PRAGMA foreign_keys=ON`, корректный `INTEGER PRIMARY KEY` для автоинкремента, транзакции, SQLite Backup API, `integrity_check`, `foreign_key_check`.

PostgreSQL: FK, Alembic, транзакции и конкурентные проверки. Изоляция типов на уровне БД требует доработки по §2.6; PostgreSQL ещё не проверен.

Модель хранится в формате редактора, поддерживает версионирование; название — 1–500 символов, описание необязательно, удаление подтверждается.

### 6.6. Экспериментальное хранилище диаграмм V14/V15

Таблицы:

- `rs_diagram_storage_version`;
- `rs_diagram_layouts`;
- `rs_diagram_nodes`;
- `rs_diagram_edges`.

Зафиксированная запись версии: `(singleton=1, version=1)`.

`rs_diagram_layouts` хранит модель, логическую базу, ревизию и время изменения.

`rs_diagram_nodes` хранит размещения объектов репозитория, координаты и размеры. Используется связь с объектом в той же логической базе.

`rs_diagram_edges` хранит технические линии диаграммы. Существующие связи репозитория отображаются отдельно и не должны автоматически копироваться в эту таблицу.

V15 предусматривает:

- до 500 узлов;
- до 2000 линий;
- длину подписи линии до 500 символов;
- проверку ревизии;
- транзакционное сохранение;
- проверку принадлежности объектов базе.

В текущей схеме и валидации отрицательные координаты запрещены. Для бесконечного поля потребуется согласованное изменение БД, сервиса и UI.

Версия хранилища сама по себе не доказывает полное соответствие схемы, индексов и ограничений.

### 6.7. Экспериментальные символы V39

Самостоятельные символы и линии с их участием хранятся в:

`rs_diagram_symbols_v39(model_id, database_id, payload)`

`payload` содержит JSON версии 1 с узлами символов и соответствующими линиями. Данные связаны с моделью и логической базой; предусмотрено совместное сохранение с содержимым V14 в рамках транзакции и ревизии.

Таблица ранее создавалась во время работы приложения при сохранении. Общую стратегию создания схемы, резервирования и миграций необходимо унифицировать и проверить.

Это экспериментальная схема, не полноценная модель BPMN и не BPMN XML.

### 6.8. Автоматическая инициализация V14

После создания основных ORM-таблиц приложение проверяет и при полном отсутствии устанавливает V14 для файловой SQLite.

Предусмотрены:

- проверка существующей базы;
- SQLite Backup API перед изменением;
- `integrity_check` и `foreign_key_check`;
- транзакционное создание схемы;
- rollback при ошибке;
- остановка при частично установленной схеме;
- проверка таблиц, столбцов и версии уже установленного V14.

Пользователь подтвердил исправление обнаруженного бага отсутствия V14. Проверка ограничений схемы, сценариев частичной установки, конкурентного запуска, восстановления и миграции старых баз остаётся необходимой.

### 9.7. Связи и потоки экспериментального верстака

Прежнее правило «все стрелки слева направо» отменено пользователем. Направление определяется реальными началом и концом связи и может быть любым.

Целевой и развиваемый сценарий:

- последовательное выделение объектов через Shift + ЛКМ;
- вызов создания связи через ПКМ или колесо V;
- построение цепочки А → Б → В;
- выбор общего или индивидуального типа потока;
- возможность добавить отдельную пару, например А → В;
- редактирование выбранной стрелки без изменения остальных;
- различение связей репозитория и технических связей диаграммы.

Экспериментальные типы потоков: `MESSAGE`, `CONTROL`, `DEFAULT`, `CONDITIONAL`.

Временная реализация V29 кодировала тип в служебной подписи вида `__RS_FLOW_V29__:<KIND>`. При развитии схемы нельзя повреждать существующие пользовательские подписи.

На символах развивались четыре контрольные точки: слева, справа, сверху и снизу. Предусматривалось создание связи кликом из одной точки в другую и отображение ортогональных линий.

Ограничения:

- выбранные стороны подключения пока не сохраняются как полноценные данные связи;
- линии могут проходить через другие символы;
- автоматический обход посторонних объектов не завершён;
- необходимо дополнительно проверить близкие и перекрывающиеся объекты, изменение размеров и работу в браузере.

### 9.8. Дорожки и подпроцессы

Развивались прозрачная дорожка, читаемая подпись, изменение размеров полями и мышью и запрет новых потоков к дорожке. Существующие линии автоматически не удаляются.

Дорожка пока не считается полноценным контейнером. Необходимо обеспечить размещение объектов внутри, отсутствие блокировки объектов прозрачной областью, корректное масштабирование, изменение размеров, согласованное перемещение содержимого, сохранение и повторное открытие.

Для подпроцесса необходимо реализовать настоящую декомпозицию: переход к вложенному содержимому, сохранение, открытие и обратную навигацию. Визуальная форма подпроцесса этого не заменяет.

## 11. Защита от ошибок и безопасность

Каждая пользовательская ошибка объясняет, что произошло, почему и что делать. Технический traceback не показывается пользователю.

### 11.1. Установка и запуск

Проверять ОС, Python и зависимости для исходников, права записи, место, WebView2, каталог данных, занятый порт, доступность БД, повреждение конфигурации, миграции, предыдущий сбой, стандартный пароль и статические ресурсы.

EXE не требует установленного Python, IDLE, pip или отдельных Python-библиотек.

При первом запуске на чистом профиле приложение самостоятельно создаёт необходимые данные и хранилище диаграмм. Пользователь не должен запускать отдельный инструмент исправления V14.

### 11.2. Валидация

- **Объекты:** название 1–500 символов, описание до 10 000, допустимый тип, дубликаты, база, запрет межбазовых и самоссылочных связей, дубликатов связей.
- **Атрибуты:** обязательное название, отсутствие дубликатов, допустимый тип, корректные числа и даты, явное сохранение, отсутствие потери старых данных и смешивания баз.
- **BPMN:** валидный XML и namespace, процесс и Start Event, предел 5 МБ, существующая база, разрешённая методология и готовый редактор.
- **Mining:** CSV до 100 МБ, не пустой, правильная кодировка, обязательные колонки, даты и достаточное число событий.
- **BPMS:** активное определение, валидная BPMN, допустимый статус, исполнитель, дедлайн и права.
- **Пользователи:** уникальный логин, сложный пароль, допустимая роль, запрет удаления последнего администратора, обязательная смена стандартного пароля.
- **Базы:** уникальное название 1–500 символов, существующая методология, подтверждение удаления и проверка моделей, объектов и связей.

Опасные операции — удаление объекта, модели, базы, пользователя, очистка, отмена процесса, переключение режима, смена методологии — требуют подтверждения. При удалении базы показывать количество моделей, объектов и связей.

Примеры сообщений: «Не удалось подключиться к базе данных»; «Объект с таким названием уже существует»; «Нельзя связывать объекты из разных баз»; «Редактор пока находится в разработке»; «База содержит объекты или модели»; «Не удалось сохранить модель. ## 12. Автономная сборка и обновления

Целевые форматы: Windows Installer, Windows Portable и исходный код.

Ближайшая задача: **архив с приложением**, который пользователь распаковывает и запускает на Windows 10/11 x64 без установленного Python и ручного исправления базы.

Для сборки `--onedir` необходимо распространять всю папку приложения, а не один EXE.

Windows Installer, ярлыки и удаление через настройки Windows остаются отдельными задачами.

Ранее использовались PyInstaller, `--onedir`, launcher `_rubik_exe_launcher_F.py` и `multiprocessing.freeze_support()`.

В последнем показанном журнале сборки использовались PyInstaller 6.22.3 и `_rubik_exe_launcher_F.py`. Присланный отдельно `build_rubik_exe.py` использовал `_rubik_exe_launcher.py` и содержал добавление `assets`. Это указывает на наличие разных вариантов сборки; фактически используемый сборщик необходимо закрепить.

EXE должна включать Python runtime, библиотеки, JS, CSS, шаблоны, изображения и иконки. WebView2 проверяется установщиком или иным понятным механизмом запуска.

Данные EXE по умолчанию хранятся в `%LOCALAPPDATA%/RUBIK_STUDIO/data/`, а не в папке установки.

При обновлении: backup, совместимая миграция, сохранение конфигурации, моделей, объектов и атрибутов, проверки целостности, совместимости ORM и функционального запуска новой EXE. Старая и новая схемы и сборки не смешиваются без проверки.

Не завершено: полная проверка актуального архива на чистой Windows 10/11 без Python, WebView2, миграция старых автономных SQLite, сохранение после обновления, установщик, удаление без потери данных, автообновление и восстановление.

GitHub Release содержит сборку/установщик, версию, изменения, требования, руководство и лицензии.

## 14. Ограничения и риски

1. NiceGUI нельзя блокировать тяжёлыми операциями; использовать подходящие фоновые механизмы.
2. SQLite ограничена при конкурентной записи; для активного Server рекомендуется PostgreSQL.
3. Лицензии bpmn-js, pm4py и SpiffWorkflow требуют проверки; SpiffWorkflow поддерживает не все BPMN-элементы.
4. Desktop ограничен localhost; Server требует проверенной авторизации.
5. Наличие типа в каталоге или пункта меню не означает готовности редактора или модуля.
6. Дополнительные редакторы реализуются постепенно; расширение каталога не должно ломать старые модели.
